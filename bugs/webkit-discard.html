WebGPU in WebKit: a fragment shader with two discards leaves garbage in the colour attachment

Each row draws a triangle whose fragment shader writes one constant colour and discards a pseudo-random share of its pixels. Every texel of the colour attachment must therefore end up either the clear value or that exact constant. The attachment is read back after each of 120 frames and anything else is counted.

Magenta marks a NaN texel, red any other unexpected value, grey the written constant, black the clear value.

Background

This was reduced from a full renderer (webgpu-aquarium), where fish drawn with an alpha-tested shader put NaN texels into the scene buffer in Safari 26.6.2 but not in Chrome. Bloom then spread each one into a visible block. What was established there, one toggle at a time:

  • Two discard statements in the one fragment shader are required. With either one alone the frame is clean; with both, ~2,600 NaN texels over 12 s. Ordinary alpha-tested transparency, which discards once, is unaffected — which is why this went unnoticed for so long.
  • The rest of the shading has to be live. Cut the shader down to the discards plus a constant, so the compiler eliminates everything else, and it is clean.
  • It is not the arithmetic. With the outputs forced to a constant, every derivative removed, and the outputs initialised before the discards, the NaN texels still appear — inside the drawn object, interleaved with texels holding the constant. A discarded fragment must not write at all, so what lands in the target is not something the shader computed.

Full reduction, in that renderer

Each line is the whole fish shader with one thing changed, run for 12-14 s against Safari 26.6.2 on an Apple M-series GPU:

both discards, shader unchanged~6,000 NaN texels
either discard aloneclean
both discards, output forced to a constant (no shading)clean
both discards, material built but nothing litclean
both discards, material + full lightingclean
everything except the final fog callclean
fog, but without its distance branchclean
that branch reinstated, but calling a shallow functionclean
the same branch calling the real one (sky, refraction, waves)FAILS

So it is not any single feature. It needs two discards and a deep, branchy call chain running after them — which is why the constructed variants below, which are all shallow, do not reproduce it. That points at shader complexity or control-flow lowering rather than at any one construct.

The one reproduction available is the renderer itself: ?only=fish&fishcut=both&watch=1 puts the two discards back and counts NaN texels on screen; dropping fishcut=both is otherwise the identical build and is clean.
